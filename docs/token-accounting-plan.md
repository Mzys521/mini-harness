# Token 计量规划

状态：待实施。当前版本只提供 Provider 用量、模型请求平均输出速度和上下文余量估算，不宣称精确预测下一次请求。

## 当前事实与限制

- Provider 返回的输入、输出、总 token 用于实际用量统计；缓存计数缺失与报告零分开处理。DeepSeek 原生 `prompt_cache_hit_tokens` 和兼容接口的缓存明细均可读取。
- Runner 记录每次成功模型请求的用量、单调时钟耗时及当时的配置窗口，通过 `model.end.metrics` 和模型步骤输出传到 Local 前端；普通对话可历史回放，临时对话只在内存中使用。
- 输出速度包含首字等待，排除工具与审批等待；失败且未返回用量的请求不会被猜测计数，无法据此保证与服务商账单一致。
- 已用 token 是一轮中多次请求的累计量。上下文余量只用最近一次请求的输入和输出减去配置窗口，不能用累计量计算。
- `ApproxTokenCounter` 仍按字符数估算；工具协议包装、多模态输入、隐藏推理、Provider 历史续接及本地配置与真实模型窗口的差异尚未统一处理。

## 实施顺序

1. **统一计量契约**：明确请求/步骤/运行/会话层级，分别记录实际用量、发送前计数、估算、未知，以及模型版本、计数器版本、数据来源。保留旧记录兼容，不能把未知写成零。
2. **模型感知计数器**：沿现有 `TokenCounter` 协议，由唯一组合根按 Provider 和模型版本装配 tokenizer；可选依赖延迟导入。无法取得匹配 tokenizer 或服务商计数 API 时保留估算标签。
3. **完整请求计数**：在 Provider 最终请求载荷边界计入 system/developer 指令、用户习惯、技能、裁剪后的历史、当前草稿、RAG、工具 schema、工具结果和协议包装；支持图片等模态时单独实现对应口径。Runner 不导入具体 Provider 或可选能力。
4. **可用窗口与预留**：验证模型真实窗口配置，分别展示总窗口占用、输出预留、安全余量和下一次可用输入预算。服务端历史续接无法展开时使用服务商计数接口或显示未知，不用累计计费用量代替。
5. **流式与对账**：区分首字延迟、生成阶段 tok/s 和当前平均请求速度；完成后用 Provider usage 校正。按请求标识去重，覆盖重试、重放、失败、取消、隐藏推理与缓存命中/未命中。不能把增量片段数当 token 数。
6. **验收与迁移**：为中英文、代码、工具、多轮裁剪、长文、空输入、取消与多模态建立计数样例；与固定 Provider/模型版本的真实用量对账并记录误差。只有口径完整且验证一致的数据标为精确，其他继续标为估算或未知。

## 验收边界

- 前端只消费带来源和统计范围的数据，不自行用字符长度生成“精确 token”。
- 发送前预算与发送后实际用量明确分开；缓存不会被误当作上下文容量节省。
- 回放、断线重连、工具续接不会重复累计；刷新后普通会话统计一致。
- 临时对话计量不进入 SQLite、长期记忆、审计或共享事件回放；清除会话时同步清除指标。
- 不增加 Runner 对 app/retrieval/mcp/platform 的反向依赖，不把计数 SDK 变成默认强制依赖。
